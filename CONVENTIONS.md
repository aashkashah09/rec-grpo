# CONVENTIONS.md — Engineering conventions and guardrails

You are implementing the **Specialist + Router** project. Read `PROJECT_PLAN.md` first —
it is the authoritative spec. This file tells you *how* to work in this repo.

## Mission context
This is a portfolio project for ML internship applications. Reviewers will read the code.
Optimize for: clarity, correctness, testability, honest reporting. Never optimize for
appearing more complete than it is.

## Hard rules
1. **Never fabricate data, metrics, or results.** No placeholder numbers presented as
   real. If a result doesn't exist yet, write "TBD (pending run)".
2. **OPE honesty:** off-policy estimators (IPS/SNIPS/DR) are applied ONLY to the single
   routing decision. Never implement or claim trajectory-level importance sampling for
   the agent. If asked to, refuse and cite PROJECT_PLAN.md §1.2.
3. **Deterministic verifiers only:** ground truth computed from the DB, value comparison
   with tolerance. Never string-match model prose.
4. **One phase at a time.** Do not implement ahead of the current phase. Each phase ends
   with tests green, CI green, and a decision record if any spec deviation occurred.
5. **Sandbox discipline:** `run_sql` uses a read-only connection with statement
   allow-list and row/time limits; `python_calc` never uses raw eval/exec on model text —
   use a restricted numeric-expression parser (e.g., ast-based whitelist).
6. **No secrets in code or logs.** All keys via env vars; `.env` gitignored;
   `.env.example` kept current.

## Code conventions
- Python ≥3.11, managed with `uv`. All deps in `pyproject.toml` (no requirements.txt).
- Full type hints on all public functions; `mypy --strict` on `src/` must pass.
- `ruff` for lint+format (line length 100). Pre-commit hooks enforce both.
- Dataclasses / pydantic models for all record types (tasks, trajectories, decisions,
  verdicts, OPE results). JSONL logs must have a versioned schema module.
- Config-driven: no experiment constants in code; everything in `configs/*.yaml`,
  loaded through one typed config module. Every run takes `--config` and `--seed`.
- Docstrings: Google style, on every module and public class/function. Docstrings should
  explain *why*, not restate the signature.
- Errors: raise typed exceptions; no bare `except`; no silent failure in verifiers,
  loggers, or estimators (these are the trust-critical paths).
- Keep functions small; prefer pure functions in `ope/`, `router/policies.py`,
  `env/verifier.py` so they are trivially testable.

## Testing requirements
- pytest; aim for near-complete coverage on `env/verifier.py`, `env/tasks.py`,
  `router/policies.py`, `router/reward.py`, `ope/` (these are the parts interviewers
  read). Serving/training code: integration-level tests with stubs.
- `tests/property/`: hypothesis-based tests for OPE estimators against a small simulator
  with analytically known policy values (assert unbiasedness in expectation for IPS,
  variance ordering SNIPS ≤ IPS empirically, DR robustness cases).
- Every task template gets a ground-truth unit test on the frozen mini fixture DB.
- Sandbox tests must include attempted escapes (DDL/DML statements, file access,
  import attempts in python_calc) asserting rejection.
- No test may call external APIs or require a GPU; gate any such test behind explicit
  markers that are skipped by default and in CI.

## Documentation requirements
- Update `README.md` incrementally at the end of each phase (section per phase).
- `docs/decisions/NNN-title.md` (ADR format: context, decision, consequences) for every
  significant choice or deviation from PROJECT_PLAN.md.
- `docs/architecture.md` maintained with a mermaid diagram of data flow.
- All figures/tables in docs generated by `src/specialist_router/analysis/` from
  committed artifacts — never hand-made.

## Git & workflow
- Conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
- Small commits per logical unit; never a single "implement phase" mega-commit.
- CI (`.github/workflows/ci.yml`): ruff, mypy, pytest (CPU-only) on every push.
- Makefile targets: `setup`, `lint`, `test`, `generate-tasks`, `serve`, `traffic`,
  `ope`, `repro-phase2`, `eval`, `report`.

## What NOT to do
- Do not add features, frameworks, or abstractions not in PROJECT_PLAN.md without an ADR.
- Do not introduce heavyweight orchestration (Airflow, Ray) — this is single-node.
- Do not write training code that only works on multi-GPU; target one GPU.
- Do not let README claims outrun artifacts.
- Do not delete or rewrite committed artifacts in `artifacts/`; append new ones.

## When uncertain
Prefer asking the user over guessing on: reward weight defaults (λ, μ), frontier API
provider choice, GPU vendor specifics, and anything touching money (API spend, GPU
rental). For pure implementation details, decide, document in an ADR, and proceed.
